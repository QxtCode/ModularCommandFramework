# UI 对接 — QML 前端接入指南

> 面向 QML 新手的入门文档。讲清楚三件事：后端暴露了哪几扇「门」、QML 怎么敲、有哪些坑。
> 目标：跑通「QML 发命令 → 后端执行 → 结果回显到界面」这一条链路。

## 〇、先做一步：把 main 的组装抽成 ShellApp（大白话教学）

> 这一节讲「为什么要封装、怎么封装才对」。代码已经帮你写好了，在 `core/ShellApp.h`。
> 就算你不接 UI，看懂这一节也能明白 main 那堆代码该怎么拆。

### 1. 为什么要抽？—— 你本来要写两遍同样的代码

先看原来的 `main.cpp`，它干的事排成一行就是：

```
加载配置 → 注册模块 → 建引擎 → 注入存储后端 → 挂 TaskManager → Run()
```

现在你要接 QML（下面第四节），会发现**前五步 QML 那边一模一样**，只有最后一步 `Run()` 不一样。如果不抽出来，你就得把「注册 PrintModule、LogModule、MetricsCollector、扫描插件目录、注册 task.result 信号」这一整段**复制粘贴到 QML 的代码里**。

以后你每加一个内置模块，就要改两个地方。漏改一处，QML 那边就报「Module not found」，还查半天。

**所以封装的目的只有一个：让「组装」这段代码只写一次，CLI 和 UI 共用。**

### 2. 抽的诀窍：只搬「组装」，不搬「运行」

这是最容易抽错的地方。新手会想「把 main 整个塞进一个类，类里一个 Run() 搞定」，结果 QML 接不进去——因为 CLI 和 UI 的**运行方式根本不同**：

| | CLI | UI（QML） |
|---|---|---|
| 引擎跑在哪 | 主线程阻塞 `Run()` | 后台 `std::thread` 跑 `RunWithoutInput()` |
| 命令怎么进来 | stdin `getline` | `InjectCommand()` 喂 |
| 结果怎么出去 | 引擎自己 `cout` | `SetResultSink()` 回调 → 发给 QML |

这三点全是「运行」的差异，不能装进同一个类里。所以 **ShellApp 的边界画在这**：

> **装进 ShellApp 的**：加载配置、注册模块、建引擎、注入存储后端、挂 TaskManager（这些 CLI 和 UI 完全一样）。
>
> **留在外面的**：`Run()` 还是 `RunWithoutInput()`、结果走 `cout` 还是走 sink（这些各自决定）。

一句话记：**ShellApp 负责「组装好」，然后把引擎交出去，调用方自己决定怎么跑。**

### 3. 三个会咬人的坑（大白话）

封装本身就是把 30 行搬个家，不难。真正麻烦的是这三个：

**坑一：存储后端必须比引擎活得久（析构顺序）。**
引擎退出时要 join 所有 Worker，Worker 收尾可能调用 `store->Save()` 存快照。如果 store 先死了，Worker 就拿着悬空指针崩掉。

大白话：像先铺地板再放家具，搬家时先搬家具再撬地板。C++ 里成员**声明顺序反过来就是析构顺序**——所以 store 要**声明在 engine 前面**（先声明 = 后析构 = 活得久）。ShellApp 里已经这么排好了，你照抄别调换顺序。

**坑二：单例只能组装一次。**
框架里的 `ModuleLifeManager`、`EventBus`、`ResultStore` 全是进程级单例。所以一个进程只能组装一次后端。

大白话：一次性打火机，点一次就完，别再点。别给 UI 做「重启内核」按钮去 stop 再 start——单例不会自动重置，会复用旧状态甚至崩。

**坑三：CLI 的「废话」要能关掉。**
`cfg.Print()`、`===== test_shell v2.7 =====` 横幅、帮助文本这些都是打印到控制台的，QML 里不该出现。所以 ShellApp 有个 `quiet` 开关，UI 传 `quiet = true`。

### 4. 已经抽好了：ShellApp 长这样

`core/ShellApp.h`，头文件里带了详细注释。用法就两行：

```cpp
// CLI —— 还是老样子，只是 main 变短了
ShellApp app(argc, argv);
app.Run();

// UI —— 换一种「跑法」，组装自动帮你做完
ShellApp app;                                   // 默认配置，不读命令行
app.GetEngine().SetResultSink([&](auto& pack){ /* 转给 QML */ });
std::thread t([]{ app.GetEngine().RunWithoutInput(); });
```

CLI 的 `main.cpp` 现在已经从 116 行瘦身到几行，组装全在 ShellApp。下面第四节接 QML 时，**不再需要「照搬 main.cpp」了**，直接拿 ShellApp 用。

## 一、对接的本质：敲三扇门

test_shell 是纯 C++ 控制台框架，它现在的「前端」是 stdin（输入）+ stdout（输出）。要换成 QML，本质是把下面三件事接到 Qt 的信号槽上：

| 后端接口 | 位置 | QML 对应的事 |
|---------|------|------------|
| `ShellEngine::InjectCommand(line)` | `core/ShellEngine.h` | 发命令（按钮点击 / 回车） |
| `ResultStore::Get().Drain()` | `core/ResultStore.h` | 收结果（显示输出） |
| `EventBus` 的 `task.result` 信号 | `core/Task.cpp` | 实时事件（进度、状态灯） |

好消息：这三扇门里有两扇已经现成——

- `InjectCommand` 线程安全、直接喂命令，原本就是测试后门（`core/ShellEngine.h`）；
- `ParmarPack` 自带 `ToJson()`（`sdk/ParmarPack.h`），`IResultFormatter` 里还躺着一个写好的 `JsonFormatter`（`core/IResultFormatter.h`）——注释写着「换 UI 就换一个 Formatter，模块不用改」。

**作者在设计时就已经为换前端留了后路。**

## 二、两个必须先懂的矛盾

### 矛盾 1：两个事件循环打架

Qt 程序靠 `app.exec()` 跑自己的事件循环；`ShellEngine::Run()` 也是阻塞循环（`core/ShellEngine.h`）。两个都占主线程 → 冲突。

**解法**：引擎放到 `std::thread` 后台线程，QML 主线程只跑 Qt 循环 + 收结果。

> **顺手禁用输入线程**：接入 UI/AI 后 stdin 用不上了（而且 `getline` 读到 EOF 会把引擎停掉）。现在有个编译时宏 `SHELL_NO_STDIN`，定义后 `Run()` 自动跳过输入线程，**不用改任何代码**。CMake 里加一行即可：
> ```cmake
> target_compile_definitions(test_shell_ui PRIVATE SHELL_NO_STDIN)
> ```
> 定义了它之后，第 2 步里的 `RunWithoutInput()` 也可以直接换成 `Run()`（效果一样）。

### 矛盾 2：结果被 cout 绑架

`ShellEngine::DrainResults()` 把每条结果 `LOG_PLAIN` 打到控制台。若照常 `Run()`，结果会被引擎自己吃掉，QML 永远拿不到。

**解法**：给结果换个出口（见第四节第 1 步）。

## 三、三种架构怎么选

| 方案 | 描述 | 复杂度 | 适用 |
|------|------|:---:|------|
| **A 同进程 + QObject 适配层** | QML 与框架编译进同一程序，QML 只通过一个 `ShellBackend : QObject` 交互 | ★ | **推荐新手** |
| B 两个进程 + 本地 socket | QML 独立进程，`QLocalSocket` 通信 | ★★★ | 要真·进程级分离时再升级 |
| C HTTP / WebSocket | 为 Web 前端 | ★★★★ | 暂不需要 |

**选 A。** 这是 Qt 官方范式——「C++ 提供 QObject，QML 消费它」。逻辑上前端分离（QML 只管 UI），物理上同进程，最好上手、改动最小。

## 四、方案 A 落地

### 数据流

```
QML 按钮 → Backend.sendCommand → engine.InjectCommand
  → 后台线程跑 MainLoop → Worker 执行 → ResultStore
  → result_sink_ 回调（JsonFormatter 格式化）
  → QMetaObject::invokeMethod(QueuedConnection) 跨线程
  → emit resultReady(json) → QML onResultReady → 显示
```

### 第 1 步：后端加两个小接口（安全区）

`MainLoop` 是雷区不能改，但**加新方法 + 给 `DrainResults` 换出口是安全区**。两处小改动，默认行为不变（不加 sink 时仍是控制台输出）。

在 `core/ShellEngine.h` 的 public 区（`Run()` 附近）加：

```cpp
/// 不启动输入线程的运行入口 —— GUI 程序里 getline(cin) 会立即 EOF
/// 把引擎停掉，所以 QML 场景只跑主循环，全靠 InjectCommand 喂命令。
void RunWithoutInput() { MainLoop(); }

/// 结果出口钩子。设置了 sink 后，结果不再打印到 cout，而是交给回调。
/// 必须在 Run()/RunWithoutInput() 启动前设置，避免线程竞争。
void SetResultSink(std::function<void(const ParmarPack&)> fn)
{
    result_sink_ = std::move(fn);
}
```

private 成员区加：

```cpp
std::function<void(const ParmarPack&)> result_sink_;   // UI 结果出口（空 = 控制台）
```

然后把 `DrainResults()` 改成「有 sink 走 sink，没 sink 走控制台」：

```cpp
// 改前：
inline void ShellEngine::DrainResults() {
    auto batch = ResultStore::Get().Drain();
    for (auto& item : batch) {
        if (item->pack)
            LOG_PLAIN(fmt_->Format(*item->pack));
    }
}

// 改后：
inline void ShellEngine::DrainResults() {
    auto batch = ResultStore::Get().Drain();
    for (auto& item : batch) {
        if (!item->pack) continue;
        if (result_sink_) result_sink_(*item->pack);
        else              LOG_PLAIN(fmt_->Format(*item->pack));
    }
}
```

> 需要 `#include <functional>`（ShellEngine.h 里通常已有，没有就补）。

### 第 2 步：ShellBackend 适配层（新文件 `ui/shell_backend.h`）

这是 QML 与后端之间的唯一桥梁。QML 只认识它，不碰任何框架类。

```cpp
// ui/shell_backend.h
#pragma once
#include <QObject>
#include <QThread>
#include <memory>
#include <string>
#include "core/ShellApp.h"   // 组装好的后端（配置+模块+引擎+存储）

class ShellBackend : public QObject {
    Q_OBJECT
public:
    explicit ShellBackend(QObject* parent = nullptr);

    Q_INVOKABLE void sendCommand(const QString& line);   // QML 发命令
    Q_INVOKABLE void start();                            // 后台线程启动引擎

signals:
    void resultReady(const QString& json);               // 一条命令的结果(JSON)

private:
    ShellApp    app_;            // 组装逻辑都在里面，不用自己建引擎/模块
    std::thread engine_thread_;
};
```

```cpp
// ui/shell_backend.cpp
#include "shell_backend.h"
#include <QMetaObject>
#include "core/IResultFormatter.h"   // JsonFormatter 就在这

ShellBackend::ShellBackend(QObject* parent)
    : QObject(parent), app_(0, nullptr, ShellApp::Options{/*quiet=*/true})
{
    // ★ 模块已经在 ShellApp 构造时组装好了，这里只做两件事：
    //   1. 设结果出口  2. 后台线程跑引擎
    ShellEngine& engine = app_.GetEngine();

    // ★ 结果出口：引擎线程回调 → 跨线程转到 QML 主线程
    //   用 JsonFormatter（框架已有的"给机器读的 JSON"），QML 端 JSON.parse 即可
    engine.SetResultSink([this](const ParmarPack& pack) {
        JsonFormatter fmt;
        QString json = QString::fromStdString(fmt.Format(pack));
        // 引擎线程里不能直接 emit —— QueuedConnection 投递到本对象所在线程
        QMetaObject::invokeMethod(this, [this, json]() {
            emit resultReady(json);
        }, Qt::QueuedConnection);
    });
}

void ShellBackend::sendCommand(const QString& line) {
    app_.GetEngine().InjectCommand(line.toStdString());   // 线程安全，直接喂
}

void ShellBackend::start() {
    engine_thread_ = std::thread([this]() { app_.GetEngine().RunWithoutInput(); });
}
```

`JsonFormatter` 输出的两种格式（QML 端按这个解析）：

```json
{"ok":true,"data":"300"}
{"ok":false,"error":{"code":404,"message":"Module not found"}}
```

### 第 3 步：组装模块 —— 不用照搬了，ShellApp 已经做了

原来这一步要「照搬 main.cpp 的组装逻辑」。现在第 〇 节已经把组装抽进了 `ShellApp`，`ShellBackend` 构造时 `app_` 自动完成了模块注册、引擎创建、存储注入，**这里什么都不用做**（就是第 2 步构造里的 `ShellApp::Options{/*quiet=*/true}`）。

> 还没看第 〇 节？建议倒回去：ShellApp 为什么这么设计、三个坑（析构顺序 / 单例一次性 / quiet）都在那。

### 第 4 步：Qt 入口 `main.cpp`

```cpp
#include <QGuiApplication>
#include <QQmlApplicationEngine>
#include <QQmlContext>
#include "ui/shell_backend.h"

int main(int argc, char* argv[]) {
    QGuiApplication app(argc, argv);

    ShellBackend backend;                    // 1. 组装后端
    backend.start();                         // 2. 后台线程启动引擎

    QQmlApplicationEngine qml;               // 3. 暴露给 QML
    qml.rootContext()->setContextProperty("Backend", &backend);
    qml.load(QUrl(QStringLiteral("qrc:/main.qml")));

    return app.exec();                       // 4. Qt 事件循环接管主线程
}
```

> 进阶：`qmlRegisterSingletonInstance("Shell", 1, 0, "Backend", &backend)` 比 `setContextProperty` 类型安全、能自动补全，跑通后再换。

### 第 5 步：前端 `main.qml`

```qml
import QtQuick
import QtQuick.Controls

ApplicationWindow {
    width: 640; height: 480; visible: true; title: "test_shell 前端"

    Column {
        anchors.fill: parent
        anchors.margins: 12
        spacing: 8

        Row {
            spacing: 8
            TextField {
                id: input
                width: 420
                placeholderText: "-m:Calc -f:add -v:a|1,b|2"
                onAccepted: Backend.sendCommand(text)      // 回车也发
            }
            Button {
                text: "发送"
                onClicked: Backend.sendCommand(input.text)
            }
        }

        TextArea {
            id: output
            width: parent.width
            height: parent.height - 60
            readOnly: true
        }
    }

    // 收结果：后端每完成一条命令 emit 一次 resultReady
    Connections {
        target: Backend
        function onResultReady(json) {
            const obj = JSON.parse(json)
            const line = obj.ok
                ? "[OK] " + obj.data
                : "[ERR " + obj.error.code + "] " + obj.error.message
            output.append(line)
        }
    }
}
```

```cmake

## 五、三个必须记住的坑

1. **跨线程发信号必须用 `QueuedConnection`**：`result_sink_` 在后台引擎线程执行，直接 `emit` 会跨线程。上面用 `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` 投递到主线程，才安全。

2. **`ParmarPack::ToJson()` 不含 error 字段**：它只序列化 `mod/func/params/success/ret`（见 `sdk/ParmarPack.h`），失败时拿不到 `error.code/message`。所以适配层里别用 `ToJson()`，用 `JsonFormatter`，它输出的 JSON 才带 `error` 对象。

3. **模块注册要照搬**：`ShellBackend` 构造里漏了 `ModuleLifeManager` 注册，QML 发 `-m:Calc` 就会报「Module not found」。第 3 步那段一个都不能少。

## 六、进阶路线

- **实时事件**：`EventBus` 的 `task.result` 信号（签名 `uint32_t, bool, int, const char*, const char*`，见 `core/Task.cpp`）能在 Worker 线程实时推送进度/完成。在 `ShellBackend` 里 link 一个 slot，同样用 `QueuedConnection` 转主线程再 `emit`。跑通基本链路后再加。

- **真·前后端分离**：把 `ShellBackend` 的 `sendCommand` / `resultReady` 换成 `QLocalServer`/`QLocalSocket` 通信，QML 变成独立进程，就是方案 B。

- **复用**：`IResultFormatter` 是策略模式，UI 需要不同格式就再加一个 Formatter，模块代码零改动。
