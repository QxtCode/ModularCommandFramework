# UI 对接 — QML 前端接入指南

> 面向 QML 新手：后端暴露了哪几扇「门」、QML 怎么敲、有哪些坑。
> 目标：跑通「QML 发命令 → 后端执行 → 结果回显到界面」链路。
> **✅ 后端链路已达成**（2026-09-11 `--selftest` 实测通过）。

## 落地说明（2026-10-24 仓库分离更新）

后端链路已验证通过（2026-09-11 `--selftest` 实测，exit=0）：
`sendCommand → InjectCommand → Worker 执行 → SetResultSink → QueuedConnection → resultReady`。
QML 侧由 `Main.qml` 的 `Connections { onResultReady(json) }` 接收同一信号并回显。

**参考实现**（完整 QML 前端 + 一个真实业务模块）已拆分到独立的产品仓库，不在本框架仓库内。
本文保留「机制教程」：ShellApp 组装（第〇节）、三扇门（第一节）、ShellBackend 适配层模式（第二节）等
对任何 UI（QML/其他 GUI 框架）通用。框架侧的对应改动：`ShellApp`（组装器）、
`RunWithoutInput` / `SetResultSink` / `EmitResult`（`core/ShellEngine.h`）。

### 两个值得知道的行为（实测得出，不是 bug）

- **`data` 为空**：模块只 `LOG_PLAIN` 不写 `return_value` 时，sink 拿到的是「结果信封」。模块内 `LOG_PLAIN` 的过程输出仍打控制台，**不走 resultReady**——模块要用 `SetResult(pack, ...)` 把结果写进信封，QML 才收得到。
- **GUI 子程序看不见 Qt 报错**：Qt 报错走 OutputDebugString，排查 QML 问题要设 `QT_FORCE_STDERR_LOGGING=1`，否则终端什么都看不到。

## 〇、先做一步：把 main 的组装抽成 ShellApp

原 `main.cpp` 干的事：`加载配置 → 注册模块 → 建引擎 → 注入存储后端 → 挂 TaskManager → Run()`。
接 QML 时**前五步一模一样**，只有 `Run()` 不同——不抽出来就得复制粘贴，以后每加一个内置模块要改两处，漏一处 QML 就报「Module not found」。

**抽的诀窍：只搬「组装」，不搬「运行」。** CLI 和 UI 的运行方式根本不同：

| | CLI | UI（QML） |
|---|---|---|
| 引擎跑在哪 | 主线程阻塞 `Run()` | 后台 `std::thread` 跑 `RunWithoutInput()` |
| 命令怎么进来 | stdin `getline` | `InjectCommand()` 喂 |
| 结果怎么出去 | 引擎自己 `cout` | `SetResultSink()` 回调 → 发给 QML |

所以 **ShellApp 装进「组装」，把引擎交出去，「运行」由调用方决定**。用法两行：

```cpp
// CLI —— main 变短了，组装全在 ShellApp
ShellApp app(argc, argv);
app.Run();

// UI —— 换一种「跑法」，组装自动做完
ShellApp app;                                   // 默认配置，不读命令行
app.GetEngine().SetResultSink([&](auto& pack){ /* 转给 QML */ });
std::thread t([]{ app.GetEngine().RunWithoutInput(); });
```

三个会咬人的坑（都已在 `core/ShellApp.h` 里处理好，照抄别改）：

1. **存储后端必须比引擎活得久（析构顺序）**：Worker 收尾可能调 `store->Save()`，store 先死就悬空。C++ 成员声明顺序反过来就是析构顺序——store 声明在 engine 前面。
2. **单例只能组装一次**：`ModuleLifeManager`/`EventBus`/`ResultStore` 是进程级单例，一个进程组装一次。别做「重启内核」按钮（stop 再 start 会复用旧状态甚至崩）。
3. **CLI 的「废话」要能关**：横幅、帮助文本不该出现在 QML 里——ShellApp 有 `quiet` 开关，UI 传 `quiet = true`。

## 一、对接的本质：敲三扇门

把三件事接到 Qt 信号槽上：

| 后端接口 | 位置 | QML 对应的事 |
|---------|------|------------|
| `ShellEngine::InjectCommand(line)` | `core/ShellEngine.h` | 发命令（按钮点击 / 回车） |
| `ResultStore::Get().Drain()` | `core/ResultStore.h` | 收结果（显示输出） |
| `EventBus` 的 `task.result` 信号 | `core/Task.cpp` | 任务完成/失败时的实时结果事件（不是逐分片进度） |

前两扇门是现成的：`InjectCommand` 线程安全（本来就是测试后门）；`IResultFormatter` 里躺着一个写好的 `JsonFormatter`（`core/IResultFormatter.h`），注释写着「换 UI 就换一个 Formatter，模块不用改」——作者设计时就为换前端留了后路。

## 二、两个必须先懂的矛盾

1. **两个事件循环打架**：`app.exec()` 和 `ShellEngine::Run()` 都是阻塞循环，都占主线程。解法：引擎放后台 `std::thread`，主线程只跑 Qt 循环。
   > 顺手禁用输入线程：编译时定义 `SHELL_NO_STDIN`，`Run()` 自动跳过输入线程（stdin 的 `getline` 读到 EOF 会把引擎停掉）。之后 `RunWithoutInput()` 也可直接换 `Run()`。
2. **结果被 cout 绑架**：`DrainResults()` 把每条结果 `LOG_PLAIN` 打控制台，QML 永远拿不到。解法：给结果换出口（第四节第 1 步）。

## 三、三种架构怎么选

| 方案 | 描述 | 复杂度 | 适用 |
|------|------|:---:|------|
| **A 同进程 + QObject 适配层** | QML 与框架编进同一程序，QML 只通过一个 `ShellBackend : QObject` 交互 | ★ | **推荐新手** |
| B 两个进程 + 本地 socket | QML 独立进程，`QLocalSocket` 通信 | ★★★ | 要真·进程级分离再升级 |
| C HTTP / WebSocket | 为 Web 前端 | ★★★★ | 暂不需要 |

**选 A**——Qt 官方范式「C++ 提供 QObject，QML 消费它」，最好上手、改动最小。

## 四、方案 A 落地

```
QML 按钮 → Backend.sendCommand → engine.InjectCommand
  → 后台线程跑 MainLoop → Worker 执行 → ResultStore
  → result_sink_ 回调（JsonFormatter 格式化）
  → QMetaObject::invokeMethod(QueuedConnection) 跨线程
  → emit resultReady(json) → QML onResultReady → 显示
```

### 第 1 步：后端的两个小接口（框架已内置）

`MainLoop` 是雷区不能改，但**加新方法 + 给 `DrainResults` 换出口是安全区**。这两个接口
已经内置于 `core/ShellEngine.h`（v2.8），接 UI 时直接调用即可，无需自己添加：

```cpp
/// 不启动输入线程的运行入口 —— GUI 程序里 getline(cin) 会立即 EOF
/// 把引擎停掉，所以 QML 场景只跑主循环，全靠 InjectCommand 喂命令。
void RunWithoutInput() { MainLoop(); }

/// 结果出口钩子。设置了 sink 后，结果不再打印到 cout，而是交给回调。
/// 必须在 Run()/RunWithoutInput() 启动前设置，避免线程竞争。
void SetResultSink(std::function<void(const ParmarPack&)> fn)
{
    result_sink_ = std::move(fn);
}
```

对应实现（供理解）：private 成员 `std::function<void(const ParmarPack&)> result_sink_;`，
`DrainResults()` 是「有 sink 走 sink，没 sink 走控制台」：

```cpp
inline void ShellEngine::DrainResults() {
    auto batch = ResultStore::Get().Drain();
    for (auto& item : batch) {
        if (!item->pack) continue;
        if (result_sink_) result_sink_(*item->pack);
        else              LOG_PLAIN(fmt_->Format(*item->pack));
    }
}
```

### 第 2 步：ShellBackend 适配层（新文件 `ui/bridge/shell_backend.h`）

QML 与后端之间的唯一桥梁，QML 只认识它：

```cpp
// ui/bridge/shell_backend.h
#pragma once
#include <QObject>
#include <QThread>
#include <memory>
#include <string>
#include "core/ShellApp.h"   // 组装好的后端（配置+模块+引擎+存储）

class ShellBackend : public QObject {
    Q_OBJECT
public:
    explicit ShellBackend(QObject* parent = nullptr);

    Q_INVOKABLE void sendCommand(const QString& line);   // QML 发命令
    Q_INVOKABLE void start();                            // 后台线程启动引擎

signals:
    void resultReady(const QString& json);               // 一条命令的结果(JSON)

private:
    ShellApp    app_;            // 组装逻辑都在里面，不用自己建引擎/模块
    std::thread engine_thread_;
};
```

```cpp
// ui/bridge/shell_backend.cpp（关键两段）
#include "shell_backend.h"
#include <QMetaObject>
#include "core/IResultFormatter.h"   // JsonFormatter 就在这

ShellBackend::ShellBackend(QObject* parent)
    : QObject(parent), app_(0, nullptr, ShellApp::Options{/*quiet=*/true})
{
    // 模块已在 ShellApp 构造时组装好，这里只做两件事：
    ShellEngine& engine = app_.GetEngine();
    // 1. 结果出口：引擎线程回调 → 跨线程转到 QML 主线程
    engine.SetResultSink([this](const ParmarPack& pack) {
        JsonFormatter fmt;
        QString json = QString::fromStdString(fmt.Format(pack));
        // 引擎线程里不能直接 emit —— QueuedConnection 投递到本对象所在线程
        QMetaObject::invokeMethod(this, [this, json]() {
            emit resultReady(json);
        }, Qt::QueuedConnection);
    });
}

void ShellBackend::sendCommand(const QString& line) {
    app_.GetEngine().InjectCommand(line.toStdString());   // 线程安全，直接喂
}

void ShellBackend::start() {
    engine_thread_ = std::thread([this]() { app_.GetEngine().RunWithoutInput(); });
}
```

`JsonFormatter` 输出格式（QML 端按这个解析）：

```json
{"ok":true,"data":"300"}
{"ok":false,"error":{"code":404,"message":"Module not found"}}
```

> 模块组装不用照搬——第〇节的 `ShellApp` 已做完（构造里的 `ShellApp::Options{/*quiet=*/true}`）。

### 第 3 步：Qt 入口 `main.cpp`

```cpp
#include <QGuiApplication>
#include <QQmlApplicationEngine>
#include <QQmlContext>
#include "ui/bridge/shell_backend.h"

int main(int argc, char* argv[]) {
    QGuiApplication app(argc, argv);

    ShellBackend backend;                    // 1. 组装后端
    backend.start();                         // 2. 后台线程启动引擎

    QQmlApplicationEngine qml;               // 3. 暴露给 QML
    qml.rootContext()->setContextProperty("Backend", &backend);
    qml.load(QUrl(QStringLiteral("qrc:/main.qml")));

    return app.exec();                       // 4. Qt 事件循环接管主线程
}
```

> 进阶：`qmlRegisterSingletonInstance("Shell", 1, 0, "Backend", &backend)` 比 `setContextProperty` 类型安全、能自动补全。

## 五、五个必须记住的坑

1. **跨线程发信号必须用 `QueuedConnection`**：`result_sink_` 在后台引擎线程执行，直接 `emit` 会跨线程。用 `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` 投递到主线程才安全。
2. **`ParmarPack::ToJson()` 不含 error 字段**：只序列化 `mod/func/params/success/ret`（`sdk/ParmarPack.h`）。适配层要用 `JsonFormatter`，它输出的 JSON 才带 `error` 对象。
3. **模块注册集中在 `ShellApp::SetupModules()`**：新模块忘了 `AddModule`，或 QML 的 `-m:` 与模块 `GetName()` 不一致，都会报 `[ERR 406] Signal not found`。例：曾出现 QML 发 `-m:SomeModule`、模块注册名却是 `OtherName`；统一命名后链路才通。新增模块时务必核对两边名字。
4. **ItemDelegate 派生组件的属性不能叫 `icon` / `label`**：基类 `AbstractButton` 自带 **FINAL** 的 `icon` 属性，同名声明会 `Cannot override FINAL property`。`qmlcachegen` 编译期不报、**运行时才炸**，且 GUI 子系统下 Qt 报错走 OutputDebugString——不设 `QT_FORCE_STDERR_LOGGING=1` 就只能看到窗口闪退。`NavButton.qml` 因此用 `iconText` / `labelText` 命名。
5. **QML 编译进 exe 资源，改了 QML 必须重编 exe**：`qt_add_qml_module` 把 QML 编进 qrc，运行时**不会**从磁盘读 `ui/qml/`。改完 QML 直接跑旧 exe，看到的报错是旧代码的——曾发生过「源码已修复、报错依旧」，其实是 exe 过期（对比 QML 与 exe 的修改时间即可确认）。

## 六、进阶路线

- **实时事件**：`EventBus` 的 `task.result` 信号（签名 `uint32_t, bool, int, const char*, const char*`，见 `core/Task.cpp`）在 Worker 线程发出，**只在任务完成或失败时发一次**（结果是最后一个分片的结果），不是逐分片进度。`ShellApp` 已 `RegisterSignal` 该信号，可以直接 link。
  想要逐分片进度，用 `task.shard_done`（签名 `uint32_t, uint32_t`）或 `task.paused`——但这两个信号目前**没有在 `ShellApp` 注册**；EventBus 对未注册信号的 `Emit` 直接返回 false（不报错），所以要先在自己的组装代码里 `RegisterSignal` 再监听。在 `ShellBackend` 里 link 时同样用 `QueuedConnection` 转主线程再 `emit`。
- **真·前后端分离**：把 `sendCommand` / `resultReady` 换成 `QLocalServer`/`QLocalSocket` 通信，QML 变独立进程，就是方案 B。
- **复用**：`IResultFormatter` 是策略模式，UI 需要不同格式就再加一个 Formatter，模块代码零改动。
