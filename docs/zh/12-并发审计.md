## 问题 A ✅ 已修复 — Emit 持锁导致连锁阻塞

**严重程度**: MEDIUM → **已修复（v2.6 A1 快照式 Emit）**
**位置**: `eventbus/include/event_bus/event_bus.h:149` (`Emit()`)

**问题**：旧 Emit 持 `bus_mutex_` shared_lock 遍历执行 Slot（可能慢）→ `RemoveSignal` 要 unique_lock 被阻塞 → `UnloadModule` 调 RemoveSignal 被阻塞 → 它又持 `module_map_` unique_lock → Dispatch/GetModule 全被阻塞。一个 200ms+ 的慢 Slot 连锁阻塞整个框架（不是死锁，锁最终释放，但严重影响可用性）。

**修复前验证**: `EmitSnapshotDoesNotBlockRemoveSignal` → RemoveSignal blocked for: **190ms**（Slot delay=200ms）

### 修复：A1 快照式 Emit

**核心思路**：Emit 在锁内只做查找 + 类型检查 + 拍快照（`shared_ptr` 拷贝信号对象），释放锁后再执行 Slot。

**前置条件（v2.4 就绪）**：① Slot 已有 `weak_ptr<ModuleBase>` 保护（当时类名为 `ModuleBaseObject`）；② `Slot::Run()` 中 `Lock()` 保证模块在 Slot 执行期间不被释放；③ `TraverseSlots()` 内部已是快照模式。

```cpp
// v2.6 A1 快照式 Emit（旧版：锁内直接 TraverseSlots）
template <class... Args>
bool Emit(const std::string& signal_name, Args&&... args)
{
    std::shared_ptr<ISignal> signal_snapshot;  // ← 快照
    SignalType* typed = nullptr;
    {
        std::shared_lock lock(bus_mutex_);
        auto it = signals_.find(signal_name);
        if (it == signals_.end()) return false;
        // … 类型检查、enabled 检查 …
        signal_snapshot = it->second;  // shared_ptr 拷贝 → ref count++
    }  // ★ 释放 shared_lock — RemoveSignal 可立即获得 unique_lock

    typed->TraverseSlots(std::forward<Args>(args)...);  // ★ 锁外执行
    return true;
}
```

**配套改动**：`signals_` 从 `map<string, unique_ptr<ISignal>>` 改为 `map<string, shared_ptr<ISignal>>`，Emit 的快照保持信号存活（即使 RemoveSignal 并发删除 map 条目）。

**修复后验证**: RemoveSignal blocked for: **0ms**；`EmitDoesNotBlockRemoveSignal_Integration` → Unload took: **0ms**（Slot delay=200ms）。

### 为什么安全

| 并发场景 | 快照式 Emit 行为 |
|----------|-----------------|
| Emit 执行中 RemoveSignal | 立即获得 unique_lock 删条目；Emit 的快照 shared_ptr 保持信号存活直到 TraverseSlots 完成 |
| Emit 执行中 UnloadModule | RemoveSignal 立即成功；Slot::Run() 的 weak_ptr::Lock() 保持模块存活 |
| 模块在 Emit 期间被删除 | Slot 的 weak_ptr 已过期 → Lock() 返回 nullptr → 跳过执行 |
| 多个 Emit 并发 | 各自 shared_lock + 快照 + 锁外执行，完全并行 |

**涉及文件**: `event_bus.h`（快照式 Emit + shared_ptr）；`concurrency_stress_test.cpp`（新增 2 测试 + 修 3 个旧测试析构时序）；`dll_lifecycle_stress_test.cpp`（修 1 个断言，不再期望 Unload 被阻塞）。

## 问题 B 🟡 无死任务检测

**严重程度**: LOW（边缘场景）｜**位置**: `core/Task.h:120` (`Step()`) / `core/ThreadPool.h:55` (`Enqueue()`)

**现象**: 模块回调死循环 → Worker 永久卡住，Pool 槽位永不归还，Cancel/Pause 只在分片间生效无法中断当前分片。后果：Worker 数递减 → 最终全部卡死。

| 潜在方案 | 思路 |
|------|------|
| B1. 看门狗线程 | 定期检查 Worker 心跳，超时 detach + 重建 |
| B2. 超时 Promise | `Submit` 返回 `future`，外部 `wait_for` 设超时 |
| B3. 分片内检查点 | 模块回调定期调 `task->CheckAlive()`（依赖模块配合，不现实）|

**建议**: B1 最实用——独立线程定期扫 Pool，`RUNNING` 超时（如 30s）→ 标记 FAILED → Release 槽位。

## 问题 C 🟢 Tick() 持锁

**严重程度**: LOW（当前无影响）｜**位置**: `core/TasksPool.h:55` (`Tick()`)

**现象**: `Tick()` 持 `mutex_` 遍历全部 Task 调 `Step()`，期间 Acquire/Release 被阻塞。main.cpp 不走此路径，保留代码备用。

**如果要修**，改为先拍快照再执行：

```cpp
void Tick(EventBus& bus) {
    std::vector<Task*> snapshot;
    { std::lock_guard lock(mutex_);
      for (auto& t : tasks_)
        if (t && t->GetState() == Task::State::RUNNING)
          snapshot.push_back(t.get());
    }
    for (auto* t : snapshot) t->Step(bus);
}
```

## 问题 D 🟡 ProcessInput 无限循环饿死 DrainResults（2026-08-17 发现）

**严重程度**: LOW（仅无限全速注入场景触发）｜**位置**: `core/ShellEngine.h` (`ProcessInput()`)

**现象**: 无限全速注入（生产 ≥ 消费）时，`ProcessInput` 的 `while(TryPop)` 永远清不空队列，主循环卡在里面，`DrainResults` 不被调，结果堆积 ResultStore（sink 收不到）。正常 CLI 交互、有限量注入不受影响。

**方案（未实施）**: 给 `ProcessInput` 加时间片，或与 `DrainResults` 交替执行。**测试层已规避**：`RampUpThroughput` 改为注入固定量。

## v2.6 修复 — /exit 崩溃（2026-08-11）

- **根因**: Shutdown() `detach` 输入线程后，线程在 `getline()` 阻塞；进程退出时 CRT 关闭 stdin，getline 返回，访问已析构的 ShellEngine 成员 → use-after-free → 0xC0000005。
- **修复**: `running_` / `input_queue_` / `cv_` / `cv_mutex_` 提升为 `ShellSharedState`，`shared_ptr` 堆上管理。输入线程持一份，ShellEngine 先析构共享状态仍存活。涉及 `core/ShellEngine.h`。

## v2.8 新增修复 — /exit 析构顺序问题（2026-08-22）

v2.8 SDK 拆分暴露两个「析构顺序 / 生命周期」问题，都只在 `/exit` 时触发。

### 修复 1：ModuleLifeManager 析构顺序（/exit 段错误）

**问题**：`/exit` 必现段错误（exit 139），且只有加载了 DLL 插件时才崩。

**根因**：成员声明顺序 `module_map_`（模块对象）在前、`dll_handles_`（DLL 句柄）在后，C++ 反序析构 → 先 `dll_handles_`（FreeLibrary 卸载 DLL）再 `module_map_`（delete 模块）→ 模块的 vtable 和析构代码在**已卸载的 DLL 里** → 段错误。热卸载 `UnloadModule()` 里一直写对了顺序（先 erase 模块再 erase 句柄），但 `= default` 析构只按声明反序，不会替你保证。

**修复**：显式析构函数，先 `module_map_.clear()`（delete 模块，DLL 仍加载）再 `dll_handles_.clear()`（FreeLibrary）。涉及 `core/ModuleLifeManager.h`。

### 修复 2：MetricsCollector 析构自清洁（magic 残留）

**问题**：进程退出时共享内存的 `magic` 残留 `0xFEEDBEEF`，外部 `shell_monitor` 误判框架仍存活。

**根因**：`magic=0` 清理只写在 `OnShutdown()` 里，而它只有热卸载会调；进程退出只 delete 模块不调 `OnShutdown`，析构里只调了 no-op 的 `StopTimer()`。

**修复**：抽私有 `Cleanup()`（`magic=0` + `shm_.reset()`），`~MetricsCollector()` 和 `OnShutdown()` 都调它——模块**任何死法都自清洁**。顺带删 v2.7 死代码（`TimerLoop`/`timer_`/`StopTimer`）。涉及 `core/MetricsCollector.h`、`test/core/monitor_integration_test.cpp`（新增 `MetricsCollectorDestructorSelfCleans`）。

### 两条通用教训

1. **DLL 插件模块的析构顺序是雷区** —— 永远先 delete 对象、再 FreeLibrary；`= default` 析构不保证这个顺序，成员声明顺序就是隐式契约。
2. **模块有两套清理路径**（`OnShutdown` 钩子 vs 析构函数），漂移就出 bug —— 原则：「析构函数兜底自清洁，`OnShutdown` 只是热卸载入口，两者走同一个清理函数」。
