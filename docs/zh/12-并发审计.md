## 问题 A ✅ 已修复 — Emit 持锁导致连锁阻塞

**严重程度**: MEDIUM → **已修复（v2.6 A1 快照式 Emit）**

**位置**: `eventbus/include/event_bus/event_bus.h:149` (`Emit()`)

### 问题描述

```
Emit() 持 bus_mutex_ shared_lock → TraverseSlots → 逐个执行 Slot（可能慢）
  ↓
RemoveSignal 需要 unique_lock → 被 Emit 阻塞
  ↓
UnloadModule 调 RemoveSignal → 被阻塞
  ↓
UnloadModule 持有 module_map_ unique_lock → Dispatch/GetModule 被阻塞
```

一个慢 Slot（200ms+）连锁阻塞整个框架。不是死锁（锁最终释放），但严重影响可用性。

### 修复前验证数据

```
ConcurrencyStress.EmitSnapshotDoesNotBlockRemoveSignal
  → RemoveSignal blocked for: 190ms (Slot delay=200ms)  ← 阻塞了 190ms
```

### 修复方案：A1 快照式 Emit

**核心思路**：Emit 在锁内只做查找 + 类型检查 + 拍快照，释放锁后再执行 Slot。

**前置条件（均已在 v2.4 就绪）**：
1. `Slot` 已有 `weak_ptr<ModuleBaseObject>` 保护 — 模块卸载后 Slot 自动跳过
2. `Slot::Run()` 中 `Lock()` weak_ptr 获取 `shared_ptr` — 模块在 Slot 执行期间不会被释放
3. `Signal::TraverseSlots()` 内部已实现快照模式（锁内拍 Slot 快照，锁外执行）

**改动**（`eventbus/include/event_bus/event_bus.h`）：

```cpp
// 旧实现 — 持锁执行 Slot
template <class... Args>
bool Emit(const std::string& signal_name, Args&&... args)
{
    std::shared_lock lock(bus_mutex_);
    auto it = signals_.find(signal_name);
    if (it == signals_.end()) return false;
    // … 类型检查、enabled 检查 …
    typed->TraverseSlots(std::forward<Args>(args)...);  // ← 锁内执行
    return true;
}

// v2.6 A1 快照式 Emit
template <class... Args>
bool Emit(const std::string& signal_name, Args&&... args)
{
    std::shared_ptr<ISignal> signal_snapshot;  // ← 快照
    SignalType* typed = nullptr;
    {
        std::shared_lock lock(bus_mutex_);
        auto it = signals_.find(signal_name);
        if (it == signals_.end()) return false;
        // … 类型检查、enabled 检查 …
        signal_snapshot = it->second;  // shared_ptr 拷贝 → ref count++
    }  // ★ 释放 shared_lock — RemoveSignal 可立即获得 unique_lock

    typed->TraverseSlots(std::forward<Args>(args)...);  // ★ 锁外执行
    return true;
}
```

**配套改动**：`signals_` 容器从 `map<string, unique_ptr<ISignal>>` 改为 `map<string, shared_ptr<ISignal>>`，使 Emit 能通过 shared_ptr 拷贝保持信号对象存活（即使 RemoveSignal 并发地删除了 map 中的条目）。

### 修复后验证

```
ConcurrencyStress.EmitSnapshotDoesNotBlockRemoveSignal
  → RemoveSignal blocked for: 0ms (Slot delay=200ms)   ← 完全不再阻塞

ConcurrencyStress.EmitDoesNotBlockRemoveSignal_Integration
  → Unload took: 0ms (Slot delay=200ms)                ← Unload 也不再阻塞
```

### 为什么安全

| 并发场景 | 快照式 Emit 行为 |
|----------|-----------------|
| Emit 执行中 RemoveSignal | RemoveSignal 立即获得 unique_lock，删除 map 条目。Emit 的快照 shared_ptr 保持信号存活直到 TraverseSlots 完成 |
| Emit 执行中 UnloadModule | RemoveSignal 立即成功，module_map_.erase() 释放模块 shared_ptr。Slot::Run() 中的 weak_ptr::Lock() 保持模块存活 |
| 模块在 Emit 期间被删除 | Slot 的 weak_ptr 已过期 → Lock() 返回 nullptr → Run() 跳过执行 |
| 多个 Emit 并发 | 各自获取 shared_lock，各自拍快照，各自锁外执行 — 完全并行 |

### 涉及文件

## 问题 B 🟡 无死任务检测

**严重程度**: LOW（边缘场景）

**位置**: `core/Task.h:120` (`Step()`) / `core/ThreadPool.h:55` (`Enqueue()`)

**现象**:
- 模块回调进入死循环 → Worker 线程永久卡住
- Pool 槽位永不归还
- Cancel/Pause 只在分片间生效，无法中断当前分片

**后果**: Worker 数递减 → 吞吐下降 → 最终所有 Worker 卡死。

**潜在方案**:
| 方案 | 思路 |
|------|------|
| B1. 看门狗线程 | 定期检查 Worker 心跳，超时 detach + 重建 |
| B2. 超时 Promise | `Submit` 返回 `future`，外部 `wait_for` 设超时 |
| B3. 分片内检查点 | 模块回调定期调 `task->CheckAlive()`，这不现实（依赖模块配合）|

**建议**: B1 看门狗最实用。独立线程定期扫 Pool，发现 `RUNNING` 超时（如 30s）→ 标记 FAILED → Release 槽位。

## 问题 C 🟢 Tick() 持锁

**严重程度**: LOW（当前无影响）

**位置**: `core/TasksPool.h:55` (`Tick()`)

**现象**: `Tick()` 持 `mutex_` 遍历全部 Task 调 `Step()`。Step 期间 Acquire/Release 被阻塞。

**状态**: main.cpp 不走 Tick 路径。保留代码以防未来需要。

**建议**: 如果要修，改为先拍快照再执行：
```cpp
void Tick(EventBus& bus) {
    std::vector<Task*> snapshot;
    { std::lock_guard lock(mutex_);
      for (auto& t : tasks_)
        if (t && t->GetState() == Task::State::RUNNING)
          snapshot.push_back(t.get());
    }
    for (auto* t : snapshot) t->Step(bus);
}
```

## v2.6 新增修复 — /exit 崩溃（2026-08-11）

- **根因**: Shutdown() 调用 `input_thread_.detach()` 后，输入线程在 `getline()` 中阻塞。进程退出时 CRT 关闭 stdin，getline 返回，线程访问已析构的 ShellEngine 成员（`running_` / `input_queue_` / `cv_`）→ use-after-free → 0xC0000005。
- **修复**: 将 `running_` / `input_queue_` / `cv_` / `cv_mutex_` 提升为 `ShellSharedState` 结构体，用 `shared_ptr` 在堆上管理。输入线程持有一份 shared_ptr，即使 ShellEngine 先析构，共享状态仍存活，线程安全检查 running 并退出。
- **涉及文件**: `core/ShellEngine.h`

## 残留小问题

**OnInit() 在 AddModule 锁外调用** (`core/ModuleLifeManager.h:57`):
- 两个线程同时 AddModule 同名模块 → 两个 `OnInit()` 都执行，只有一个模块存活
- 如果 `OnInit()` 有重量级副作用（开文件、启动线程），会浪费资源
- 不影响正确性（只有一个模块注册到 EventBus）
