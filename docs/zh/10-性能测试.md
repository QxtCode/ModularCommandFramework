## Release 真实吞吐（2026-09-01 实测，权威）

> 本节是 **Release /O2** 实测，框架真实水平（Debug→Release 典型提升 5×）。
> 下方「Debug 峰值吞吐」章节仅供开发期参考。

**结论：Release 稳态吞吐 ≈ 10 万 cmd/s，最佳 10.6 万。**

| 注入量 N | 平均吞吐 | 最佳吞吐 | 拒绝率 | 处理时间 |
|---------|---------|---------|--------|---------|
| 1,000 | 27,443 | 28,031 | 14% | 31ms |
| 5,000 | 68,793 | 70,117 | 14% | 61ms |
| 20,000 | 96,332 | 100,577 | 15% | 172ms |
| **50,000** | **102,739** | **106,383** | 14% | 407ms |

### 测量条件
- 编译：`cmake --preset release`（MSVC 19.44, /O2, C++20）
- 引擎：14 workers + 14 池槽（`hardware_concurrency() - 2`），`RunWithoutInput()`
- 模块：快模块 `nop`（<1μs），命令 `-m:PeakFast -f:nop`
- 完成判据：**池子全空闲**（`FreeTasks() == TotalTasks()`），不用 `completed < N*9/10`
- 完成数统计：`SetResultSink` + `atomic<int>` 计数器（不查 ResultStore）
- **stdout 重定向到 /dev/null**（消除每命令 `--- [Mod.func] ---` 的互斥 cout 拖慢，见坑 1/6）
- 每档多轮（5 或 3 轮），取平均与最佳

### 关键规律：N 越大吞吐越高，直到收敛

N 小时**启动开销**（线程唤醒、cv 冷启动、池预热）占比大：N=1000 只有 2.7万；N=50000 达 10.3万（启动开销被摊平），N=20000→50000 从 9.6万涨到 10.3万趋于收敛 → **稳态 ~10万**。
**结论：报吞吐必须注明 N。小 N 的数字偏低，不代表稳态。**

### 拒绝率 ~14% 是池容量固有限制

14 槽全速注入，约 14% 命令被 `Acquire()` 拒绝（返回 null → drop）。吞吐 = `completed / time`，是「实际处理完成」的真实吞吐，不含被拒命令。

## 测量踩坑记录（重要，避免重复踩）

### 坑 1：stdout 噪声是头号杀手，350× 差距

`IModule::Execute` 在调 Slot lambda **之前**检查 `pack->show_explanation`（`sdk/IModule.h:127`），
为 true 时每命令 `LOG_PLAIN("--- [Mod.func] ---")` —— 无条件 `std::cout` + `endl` + 全局 `OutputMutex`，多 Worker 高频下是灾难性序列化点：

| stdout 状态 | 吞吐 |
|------------|------|
| 写终端（默认） | **~280 cmd/s** |
| 重定向到 /dev/null | **~10万 cmd/s** |

**差 350×。** 测吞吐必须把 stdout 重定向走。

> **`show_explanation = false` 在 Slot lambda 里设无效** —— Execute 在调 lambda 之前就检查了。要关得在解析阶段改 pack 默认值（`ParmarPack.h:61`），或压测时直接重定向 stdout。

### 坑 2：完成判据用阈值会 flaky

`peak_stress_test.cpp::RampUpThroughput` 用 `completed < N*9/10` 作等待退出条件。
但池满拒绝 ~14%，`completed` 常到不了 90% 阈值 → 等待循环**空转到 1000×10ms=10s 上限**，
10s 灌进分母 → 吞吐显示 280 cmd/s（假数字）；偶尔碰巧够阈值又提前退出 → 显示 15万（乐观数）。
**同一个测试能跑出 280 和 15万，差 500×，不可信。**

可信判据：**池子全空闲**（`FreeTasks() == TotalTasks()`）—— 任务都归还 = 处理完，不依赖完成阈值。

### 坑 3：探针法对 <1μs 命令失真

`PERF_SCOPE`（`steady_clock::now()` 两次 + 原子累加）的开销与 nop 命令同量级，海森堡式失真（且 `thread_local` 累加器跨线程汇总会丢）。**<1μs 的极快命令不宜用函数级时钟探针测占比**，要测得用更粗粒度区间计时或采样。

### 坑 4：Git Bash `cmd //c` 管道缓冲 stderr

`fprintf(stderr)` 经过 `cmd //c` 管道不实时（程序在跑但看不到输出，误判卡死）。独立 perf 程序的结论应**写文件**，不依赖终端实时输出。

### 坑 5：Debug vs Release 必须分清

Debug 没优化（无内联、带调试信息、assert 开销），不能代表框架真实水平。**报性能前先确认编译类型，Release 才是真实水平。**

### 坑 6：stdout 重定向到「文件」≠ /dev/null

坑 1 只对比了「终端 vs /dev/null」；重定向到**文件**时结果天差地别（2026-09-01 复测发现）：

| stdout 目标 | RampUp 结果 | completed/5000 | 吞吐 | 现象 |
|------------|------------|----------------|-----------|------|
| `/dev/null` | ✅ 通过断言 | >2500 | 不可见* | Worker 不受拖累 |
| **文件**（真实磁盘 I/O）| ❌ **FAILED** | **800~1288** | **51~82 cmd/s** | Worker 被 cout 串行化 |

\* 数字走 stdout，重定向 /dev/null 后丢失，故不可见。

**根因**：`LOG_PLAIN` 的 `std::endl` 每命令强制 flush。重定向到文件时 flush 触发真实磁盘 write syscall + 仍持全局 `OutputMutex` 串行化 14 个 Worker → 单命令被拖到 ~100ms/cmd；`/dev/null` 下写入被内核丢弃，无 I/O 阻塞。RampUp 判据 `completed > N/2`（2500）：文件下 10s 只完成 ~1000 < 2500 → FAIL。

**结论**：
1. 测吞吐「重定向 stdout」**目标必须是 `/dev/null`（或 `nul`）**，不是文件——文件仍会因 flush 拖慢，且能让 flaky 测试从通过变失败。
2. 想既消除噪声**又保留数字**：测量数字走 `stderr` 或写文件（`std::ofstream`），stdout 独立重定向 /dev/null。

## 限制与调优

| 现象 | 机制 | 调优 |
|------|------|------|
| **池耗尽** | 所有 Task 槽被占，`Acquire()` 返回 null，引擎输出 `[ERROR] All tasks busy` 并跳过 | 增大 `pool_size` 或 `--pool_size=N` |

| **主循环周期** | `WaitForWork()` 100ms 超时是结果可见性最小延迟 | 降低超时减延迟，但增加空闲 CPU；改 `ShellEngine::WaitForWork()` 参数 |

## 任务持久化性能（2026-09-01 实测）

> 隔离测试见 `test/core/task_persistence_perf_test.cpp`。后端：`MemPersistence`（内存 map+mutex）vs `TaskFilePersistence`（文件 I/O）。环境：Release /O2，i7-13700H，14 workers。

### 单次 Save/Load 耗时（后端本身）

```
Mem  Save: 0.25 us/op   Load: 0.06 us/op
File Save: 257 us/op    Load: 67 us/op     ← File 比 Mem 慢 ~1000×
```

（文件 I/O + mutex + 文本 key=value 解析 vs 内存 map 插入。）

### 批量存储 + 加载总用时

| 任务数 N | Mem 总用时 | File Save | File Load | **File 总用时** |
|---------|-----------|-----------|-----------|----------------|
| 100 | ~0 ms | 18 ms | 7 ms | **0.025 秒** |
| 1000 | ~0 ms | 201 ms | 68 ms | **0.269 秒** |
| 5000 | 1 ms | 1232 ms | 372 ms | **1.604 秒** |

线性增长，每任务约 0.32 ms。`LoadAll` 正确加载全部 N 条非终态记录。

### 持久化对框架吞吐的影响

```
Null（无持久化）: ~34,300 cmd/s  ← 基线
Mem（内存）:      ~33,500 cmd/s
File（文件）:      ~33,500 cmd/s   ← File 对吞吐几乎无影响（<1%）
```

**原因**：测试里 Save 在 `SetResultSink` 回调中（主循环消费线程），**不在 Worker 热路径上**——Save 开销落在消费端，不阻塞处理。真实框架的 Save 时机是 Worker 收尾检测到 PAUSED 时（热路径），但只对**暂停的任务**触发，实际影响比本测试的「每结果都 Save」更小——本测试是最坏情况下界。

### 结论

| 维度 | File 持久化 | Mem 持久化 |
|------|-----------|-----------|
| 单次 Save 耗时 | 257 us | 0.25 us |
| 5000 任务存+加载总用时 | **1.6 秒** | 1 ms |
| 对框架吞吐影响 | <1%（几乎无） | <1% |

**文件持久化的代价在「存储/加载本身」（I/O），不在「对框架吞吐的影响」**：恢复 5000 个暂停任务要 ~1.6s I/O，但正常跑任务时持久化几乎不拖慢框架。

> **测试局限**：上表吞吐绝对值（~3.4万）被 stdout 噪声压低（纯框架 ~10万），但 Null/Mem/File 三组承受相同噪声，**相对结论有效**——绝对值与相对值的区分见坑 1。

> 失败的 `RampUpThroughput` **不可信**——`> /dev/null` 时 PASS（completed>2500 巧合过阈值，但 throughput 是空转灌水假数）；`> 文件` 时 FAIL（坑 6 拖慢 + 坑 2 判据空转，completed 卡 800~1288 < 2500）。

> 其余 5 个（Burst/Sustained/PoolUtil/Recovery/SlotException）稳定 PASSED。可信的稳态 ~10万 cmd/s 见「Release 真实吞吐」章节。修复 RampUp = 改「池空闲」判据 + N≥20000（见下方可信测法）。

### 可信吞吐测法（写新性能测试时遵循）

1. **完成判据用「池子全空闲」**：`engine.FreeTasks() == engine.TotalTasks()`，不依赖 `completed` 阈值（池满拒绝会让阈值永不满足）。
2. **完成数用 `SetResultSink` + `atomic<int>` 计数**，不查 ResultStore（结果一进去就被 DrainResults 消费，查残留只拿到尾巴）。
3. **stdout 重定向到 `/dev/null` / `nul`**（不是文件！见坑 1/6，350× 差距）。
4. **N ≥ 20000** 摊平启动开销，小 N 吞吐偏低不代表稳态。
5. **多轮取平均 + 最佳**，单轮波动大。

### 写测试的约定：优先复用已有案例

- 新测试优先加进 `test/` 已有套件，复用 fixture/辅助函数（`RegisterFastModule`、`AggressiveCleanup`、`StressWorkers`），不重复造轮子；覆盖不了才新建文件并加进 `test/CMakeLists.txt`。
- **不要为性能测量单独建可执行目标**——gtest 用 `--gtest_filter` 就能单独跑。临时测量程序跑完即删。
