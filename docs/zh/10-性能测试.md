## Release 真实吞吐（2026-09-01 实测，权威）

> 下方「峰值吞吐」章节是 **Debug** 数据，仅供开发期参考。
> 本节是 **Release /O2** 实测，是框架的真实水平。Debug→Release 典型提升 5×。

**结论：Release 稳态吞吐 ≈ 10 万 cmd/s，最佳 10.6 万。**

| 注入量 N | 平均吞吐 | 最佳吞吐 | 拒绝率 | 处理时间 |
|---------|---------|---------|--------|---------|
| 1,000 | 27,443 | 28,031 | 14% | 31ms |
| 5,000 | 68,793 | 70,117 | 14% | 61ms |
| 20,000 | 96,332 | 100,577 | 15% | 172ms |
| **50,000** | **102,739** | **106,383** | 14% | 407ms |

### 测量条件
- 编译：`cmake --preset release` + `cmake --build --preset release`（MSVC 19.44, /O2, C++20）
- 引擎：14 workers + 14 池槽（`hardware_concurrency() - 2`），`RunWithoutInput()`
- 模块：快模块 `nop`（<1μs），命令 `-m:PeakFast -f:nop`
- 完成判据：**池子全空闲**（`FreeTasks() == TotalTasks()`），不用 `completed < N*9/10`
- 完成数统计：`SetResultSink` + `atomic<int>` 计数器（不查 ResultStore）
- **stdout 重定向到 /dev/null**（消除每命令 `--- [Mod.func] ---` 的互斥 cout 拖慢，见下方「stdout 噪声」坑）
- 每档多轮（5 或 3 轮），取平均与最佳

### 关键规律：N 越大吞吐越高，直到收敛
N 小时**启动开销**（线程唤醒、cv 冷启动、池预热）占比大，吞吐被压低：
- N=1000 只有 2.7万（33ms 里启动开销占大头）
- N=50000 达 10.3万（407ms 里启动开销被摊平）
- N=20000→50000 从 9.6万涨到 10.3万，趋于收敛 → **稳态 ~10万**

**结论：报吞吐必须注明 N。小 N 的数字偏低，不代表稳态。**

### 拒绝率 ~14% 是池容量固有限制
14 槽全速注入，约 14% 命令被 `Acquire()` 拒绝（返回 null → drop）。
吞吐 = `completed / time`，是「实际处理完成」的真实吞吐，不含被拒命令。

## 测量踩坑记录（重要，避免重复踩）

### 坑 1：stdout 噪声是头号杀手，350× 差距
`IModule::Execute` 在调 Slot lambda **之前**检查 `pack->show_explanation`（`sdk/IModule.h:127`），
为 true 时每命令 `LOG_PLAIN("--- [Mod.func] ---")` —— 无条件 `std::cout` + `endl` + 全局 `OutputMutex`。
多 Worker 高频下，这是灾难性序列化点：

| stdout 状态 | 吞吐 |
|------------|------|
| 写终端（默认） | **~280 cmd/s** |
| 重定向到 /dev/null | **~10万 cmd/s** |

**差 350×。** 测吞吐必须把 stdout 重定向走（`> /dev/null` 或 `> nul`）。

> **`show_explanation = false` 在 Slot lambda 里设无效** —— Execute 在调 lambda 之前就检查了，
> lambda 里设 false 已经晚了，标题已打。要关得在解析阶段改 pack 默认值（`ParmarPack.h:61`），
> 或压测时直接重定向 stdout。

### 坑 2：原版 RampUp 测试完成判据 flaky
`peak_stress_test.cpp::RampUpThroughput` 用 `completed < N*9/10` 作等待退出条件。
但池满拒绝 ~14%，`completed` 常到不了 90% 阈值 → 等待循环**空转到 1000×10ms=10s 上限**，
10s 灌进分母 → 吞吐显示 280 cmd/s（假数字）。偶尔 completed 碰巧够阈值又提前退出 → 显示 15万（乐观数）。
**同一个测试能跑出 280 和 15万，差 500×，不可信。**

可信判据：**池子全空闲**（`FreeTasks() == TotalTasks()`）—— 任务都归还 = 处理完，不依赖完成阈值。

### 坑 3：探针法对 <1μs 命令失真
用 `PERF_SCOPE`（`steady_clock::now()` 两次 + 原子累加）测四环节占比时，
探针开销与 nop 命令本身同量级，海森堡式失真。带探针时吞吐被压低（且 `thread_local` 累加器跨线程汇总会丢）。
**<1μs 的极快命令不宜用函数级时钟探针测占比**，要测得用更粗粒度的区间计时或采样。

### 坑 4：Git Bash `cmd //c` 管道缓冲 stderr
`fprintf(stderr)` 经过 `cmd //c` 管道时不实时（程序在跑但看不到输出，误判卡死）。
独立 perf 程序的结论应**写文件**（`std::ofstream`），不依赖终端实时输出。

### 坑 5：Debug vs Release 必须分清
下方「峰值吞吐 ~21,000」是 **Debug** 数。Debug 没优化（无内联、带调试信息、assert 开销），
不能代表框架真实水平。**报性能前先确认编译类型，Release 才是真实水平。**

### 坑 6：stdout 重定向到「文件」≠ /dev/null（2026-09-01 复测发现）
坑1说「重定向 stdout」消除噪声拖慢，但**重定向目标不同，结果天差地别**——
这是坑1没说清、复测才暴露的细节：

| stdout 目标 | RampUp 结果 | completed/5000 | throughput | 现象 |
|------------|------------|----------------|-----------|------|
| `/dev/null`（丢弃写入）| ✅ 通过断言 | >2500 | 不可见* | Worker 不受拖累，完成多 |
| **文件**（真实磁盘 I/O）| ❌ **FAILED** | **800~1288** | **51~82 cmd/s** | Worker 被 cout 串行化，10s 仅完成 ~1000 |

\* 数字走 stdout，重定向 /dev/null 后丢失，故不可见。

**根因**：`LOG_PLAIN` 的 `std::cout << ... << std::endl`，`endl` 每命令强制 flush。
重定向到**文件**时，flush 触发真实磁盘 write syscall + 仍持全局 `OutputMutex` 串行化 14 个 Worker →
单命令被拖到 ~100ms/cmd。`/dev/null` 下写入被内核丢弃，无真实 I/O 阻塞，Worker 快得多。

**为什么 RampUp 从「通过」变「失败」**：RampUp 判据 `completed > N/2`（2500）。
- `/dev/null`：Worker 快，completed 涨过 2500 → 通过（但 throughput 仍是空转灌水的假数，见坑2）。
- 文件：Worker 被 cout 拖到 ~100ms/cmd，10s 空转期内只完成 ~1000 条 < 2500 → **断言失败**。

**结论**：
1. 测吞吐「重定向 stdout」时，**目标必须是 `/dev/null`（或 `nul`）**，不是普通文件。
   重定向到文件仍会因 cout flush 拖慢，且可能让 flaky 测试从通过变失败。
2. 想既消除噪声**又保留数字**，不能靠 stdout 重定向（噪声和数字同走 stdout）——
   要让测量数字走 `stderr` 或写文件（`std::ofstream`），stdout 独立重定向 /dev/null。
3. 这是坑1的细化：坑1只对比了「终端 vs /dev/null」（350×），没提「文件 vs /dev/null」的差异。
   复测时 `> /tmp/peak.log` 让 RampUp 稳定失败，才暴露此坑。

## 限制与调优

### 池耗尽

当所有 Task 槽位被占用时, `TasksPool::Acquire()` 返回 `nullptr`。
引擎输出 `[ERROR] All tasks busy` 并跳过命令。

**调优:** 增大 `pool_size` 或 `--pool_size=N`。

### 工人饱和

当所有工人忙碌时, 任务在线程池中排队。线程池队列无限 —
极端情况下可能导致内存增长。

**调优:** 增大 `workers`。经验公式: `workers = CPU核心数 - 2`。

### 主循环周期

`WaitForWork()` 超时 (100ms) 是结果可见性的最小延迟。
降低超时可减少延迟, 但会增加空闲 CPU 使用。

**调优:** 修改 `ShellEngine::WaitForWork()` 超时参数。

### v2.6 改进: 不再有 Emit 阻塞

快照式 Emit 消除了慢 Slot 对 RemoveSignal/UnloadModule/Dispatch 的连锁阻塞。
模块卸载不再需要等待慢回调完成，可用性大幅提升。
详见 [12-并发审计](12-并发审计.md)。

## 任务持久化性能（2026-09-01 实测）

> 测试任务存储/加载对框架的影响。隔离测试见 `test/core/task_persistence_perf_test.cpp`。
> 后端：`MemPersistence`（内存 map+mutex）vs `TaskFilePersistence`（文件 I/O，每任务一个 `task_<id>.dat`）。
> 环境：Release /O2，i7-13700H，14 workers。

### 单次 Save/Load 耗时（后端本身）

```
Mem  Save: 0.25 us/op   Load: 0.06 us/op
File Save: 257 us/op    Load: 67 us/op
File 比 Mem 慢 ~1000×
```

文件持久化单次 Save 257 微秒（文件 I/O + mutex + 文本 key=value 解析），
Mem 0.25 微秒（内存 map 插入）。**单次操作 File 比 Mem 慢约 1000 倍。**

### 批量存储 + 加载总用时

| 任务数 N | Mem 总用时 | File Save | File Load | **File 总用时** |
|---------|-----------|-----------|-----------|----------------|
| 100 | ~0 ms | 18 ms | 7 ms | **0.025 秒** |
| 1000 | ~0 ms | 201 ms | 68 ms | **0.269 秒** |
| 5000 | 1 ms | 1232 ms | 372 ms | **1.604 秒** |

**5000 个任务全量存储 + 加载，File 总用时 1.6 秒**（Save 1.2s + Load 0.37s），Mem 仅 1 ms。
线性增长，每任务约 0.32 ms。`LoadAll` 正确加载全部 N 条非终态记录。

### 持久化对框架吞吐的影响

```
Null（无持久化）: ~34,300 cmd/s  ← 基线
Mem（内存）:      ~33,500 cmd/s
File（文件）:      ~33,500 cmd/s
```

**File 持久化对框架吞吐几乎无影响（<1% 下降），和 Mem 一样。**

**原因**：测试里 Save 在 `SetResultSink` 回调中（主循环 DrainResults 消费线程），
**不在 14 个 Worker 的处理热路径上** —— Worker 全速处理推结果，Save 开销落在消费端，
不阻塞处理。所以即使 File 单次 Save 要 257 us，也不拖慢吞吐。

> **真实框架的 Save 时机**是 Worker 收尾检测到 PAUSED 时（在 Worker 线程，热路径上），
> 但只对**暂停的任务**触发，不是每任务都 Save，实际影响比本测试的「每结果都 Save」更小。
> 本测试是「最坏情况」下界。

### 结论

| 维度 | File 持久化 | Mem 持久化 |
|------|-----------|-----------|
| 单次 Save 耗时 | 257 us | 0.25 us |
| 5000 任务存+加载总用时 | **1.6 秒** | 1 ms |
| 对框架吞吐影响 | <1%（几乎无） | <1% |

**文件持久化的代价主要在「存储/加载本身」（I/O 耗时 1.6s/5000任务），
不在「对框架吞吐的影响」** —— 因为 Save 不在 Worker 热路径。
恢复 5000 个暂停任务要花 ~1.6 秒做 I/O，但正常跑任务时持久化几乎不拖慢框架。

> **测试局限**：上表吞吐绝对值（~3.4万）被 stdout 噪声压低（纯框架 ~10万），
> 但 Null/Mem/File 三组承受相同噪声，**相对结论「File 不拖慢吞吐」有效**。
> 拿绝对吞吐需重定向 stdout（见「踩坑记录」坑 1）。

### 复测数据（2026-09-01，stdout→文件，3 轮）

> 复测注：本次用「stdout 重定向到文件」（非 /dev/null）方式跑，受坑6拖累，绝对值偏低，
> 但**相对结论与结论表一致**，且数值比初测略快（环境差异内）。

| 维度 | 初测（/dev/null）| 复测（→文件）| 说明 |
|------|----------------|-------------|------|

| File/Mem Save 比 | ~1000× | **659×** | Mem Save 0.278us |

| 持久化对吞吐 Null | ~34,300 cmd/s | avg 17,341 / best 19,506 | 文件 stdout 噪声压低 |

> 失败的是 `RampUpThroughput`，**稳定复现**（连跑 3 轮一致）：
>
> | 运行方式 | 结果 | completed/5000 | throughput | 耗时 |
> |---------|------|----------------|-----------|------|
> | `> /dev/null`（文档推荐）| ✅ PASS | >2500 | 不可见* | 全套 28.6s |
> | `> /tmp/peak.log`（文件）| ❌ **FAIL** | 800~1288 | 51~82 cmd/s | RampUp 单测 15.5s |
>
> \* 数字走 stdout，重定向 /dev/null 后丢失，故不可见。
>
> **失败根因 = 坑2（flaky 判据）× 坑6（文件 stdout 拖慢）双重作用**：
> - 判据 `completed < N*9/10`（<4500）永不满足 → 空转到 10s 上限（坑2）。
> - stdout→文件时 `LOG_PLAIN` 的 `endl` flush 串行化 14 Worker → 10s 仅完成 ~1000 条，
>   `completed` 卡在 800~1288 < 断言阈值 2500 → FAIL（坑6）。
> - `/dev/null` 丢弃写入，Worker 快，completed 涨过 2500 → 巧合通过断言，
>   但打印的 throughput 仍是空转灌水的假数（~430 cmd/s 量级）。
>
> **结论**：当前 `RampUpThroughput` **不可信**——通过与否取决于 stdout 重定向目标，
> 通过时数字也是假的。其余 5 个测试（Burst/Sustained/PoolUtil/Recovery/SlotException）
> 均稳定 PASSED。可信的稳态吞吐 ~10万 cmd/s 见上方「Release 真实吞吐」章节
> （专用测量，池空闲判据 + /dev/null）。**修复 RampUp 需改判据为「池空闲」+ N≥20000**（见下方可信测法）。

### 可信吞吐测法（写新性能测试时遵循）

原版 `RampUpThroughput` 的完成判据 `completed < N*9/10` 在 N 超池容量时 flaky
（空转灌水分母）。写吞吐测试时用以下模式：

1. **完成判据用「池子全空闲」**：`engine.FreeTasks() == engine.TotalTasks()`，
   不依赖 `completed` 达到某个阈值（池满拒绝会让阈值永不满足）。
2. **完成数用 `SetResultSink` + `atomic<int>` 计数**，不查 ResultStore
   （结果一进去就被 DrainResults 消费，查残留只拿到尾巴）。
3. **stdout 重定向**：`> /dev/null`（Linux）或 `> nul`（Windows），
   消除 `--- [Mod.func] ---` 的互斥 cout 拖慢（350× 差距，见「踩坑记录」坑 1）。
4. **N 要够大**（≥20000）以摊平启动开销，小 N 的吞吐偏低不代表稳态。
5. **多轮取平均 + 最佳**，单轮波动大。

### 写测试的约定：优先复用已有测试案例

- **新测试优先加到 `test/` 已有的测试文件 / 测试套件里**，复用已有的 fixture、辅助函数
  （如 `RegisterFastModule`、`AggressiveCleanup`、`StressWorkers`），不重复造轮子。
- 只有当现有套件覆盖不了新场景时，才新建测试文件，并在 `test/CMakeLists.txt` 的
  `add_executable(test_runner ...)` 列表里添加源文件。
- **不要为性能测量单独建可执行目标**（如 perf_real）—— 除非测量逻辑确实无法用 gtest
  表达。gtest 测试用 `--gtest_filter` 就能单独跑，无需独立 target。临时测量程序跑完即删，
  不留在 CMakeLists 里。
