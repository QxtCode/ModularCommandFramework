# v2.7 架构概览 — ShellEngine + ResultStore

## 相比 v2.4 的变化

v2.4 用 `std::queue<Task*>`（done_queue）把结果从工人传给主线程。每个结果都要等主线程 drain 完了 task 槽位才释放。

v2.5 引入两个新组件，把生产和消费彻底解耦：

| 组件 | 职责 |
|------|------|
| **ResultStore** | 单例数据仓库。工人 Push 结果；消费者按自己节奏 Drain。 |
| **ShellEngine** | 封装事件循环：`DrainResults → FlushMetrics → WaitForWork → ProcessInput`。 |

## 数据流向

```
输入 "-m:Calc -f:add -v:a|1,b|2"
  │
  ├─ 输入线程 (getline) ──→ LockQueue<string> ──→ ShellEngine::ProcessInput
  │                                                       │
  │                                              CommandParser::SendCommand
  │                                                       │
  │                                              TasksPool::Acquire →
  │                                              ThreadPool::Enqueue
  │                                                       │
  │                                              工人线程:
  │                                                while(task->Step(bus)) {}
  │                                                │
  │                                   ┌────────────┴────────────┐
  │                                   │                         │
  │                            bus.Emit("task.result")   ResultStore::PushResult
  │                            (实时订阅者)              (批量可消费数据)
  │                                                             │
  │                                              ShellEngine::DrainResults
  │                                                → Formatter → LOG_PLAIN
  │
  └─ ShellEngine::WaitForWork
       cv.wait_for(HasResults || input || !running)
```

## 三条独立通路

```
工人完成
  ├─ bus.Emit("task.result"...)  → EventBus 订阅者（实时，零延迟）
  ├─ PushResult                  → ResultStore（仓库，批量消费）
  └─ tasks.Release(task)         → 池槽位立即可复用
```

三条通路各司其职、互不冲突：
- 订阅 EventBus → 实时推送（监控、告警、链式调度）
- Drain ResultStore → 批量结构化消费（CLI 输出、UI 绑定、测试断言）
- 不再需要主线程 bottleneck — task 槽位在工人完成瞬间就归还池子

## ShellEngine — 四步流水线

```cpp
void ShellEngine::MainLoop() {
    while (running_) {
        DrainResults();   // ① ResultStore 批量取 → 格式化 → 输出
        FlushMetrics();   // ② MetricsCollector → 共享内存
        WaitForWork();    // ③ cv.wait_for(HasResults || input || !running)
        ProcessInput();   // ④ input → 解析 → 提交任务
    }
}
```

每步一个职责。再也不需要在一个函数里同时理解锁、队列和 cv 谓词。

## ResultStore — 数据仓库

```cpp
// 生产者（工人线程）
ResultStore::Get().PushResult(task_id, pack_copy);

// 消费者（主线程 / UI 线程）
auto batch = ResultStore::Get().Drain();   // O(1) swap
for (auto& item : batch) { ... }

// 谓词安全查询（无副作用）
bool has = ResultStore::Get().HasResults();
```

关键设计：`HasResults()` 是只读查询，可以被 `cv.wait_for` 谓词多次安全调用，不会像 `Drain()` 那样产生副作用导致数据丢失。

## 配置

`ShellConfig` 在 `ShellEngine` 启动前从 INI 文件和命令行加载参数：

```cpp
ShellConfig cfg;
cfg.LoadFromFile("test_shell.cfg");   // 可选 — 不存在则用默认值
cfg.ApplyArgs(argc, argv);            // --pool_size=16 --workers=8

ShellEngine engine(cfg.pool_size, cfg.workers);
```

优先级：`命令行参数 > 配置文件 > 内置默认值`。

`log_level` 字段在模块注册后应用到 `LogModule`，覆盖 `log.conf` 设置。

完整参数参考见 [10-性能测试](10-性能测试.md)。

## 任务持久化 — 暂停 / 保存 / 恢复 (v2.7)

v2.7 完成了 v2.6 只画出草图的"暂停存储"闭环。暂停的任务现在会快照到可插拔的
`ITaskPersistence` 后端，`resume` 能从断点重建，而不是丢失。

```
pause 命令 → task->Pause()
  → Worker 跑完当前分片 → Step() 返回 false
  → Worker 收尾：若 PAUSED && store_ → store_->Save(task->ExportRecord())
  → Release(task)                             // 槽位归还

resume 命令 → store->Load(id) → pool.Acquire → task->Restore(rec)
  → Resume → Enqueue → 从断点继续
```

| 组件 | 职责 |
|------|------|
| `ParmarPack::ToJson/FromJson` | 手写 JSON 子集，序列化分片 |
| `Task::ExportRecord()` | 把当前分片序列化进 `TaskRecord.shards_json` |
| `Task::Restore()` | 从 `shards_json` 反序列化回真实分片 |
| `ITaskPersistence` | 可插拔快照后端（Save/Load/Delete/LoadAll/GC） |
| `ShellEngine::SetTaskPersistence` | 注入后端；Worker 收尾在暂停时保存 |

后端由 `main.cpp` 注入，默认 `nullptr`（纯内存，行为与 v2.5 一致）。
开发者实现接口需满足的约束见 [05-任务系统](05-任务系统.md)。

## 安全防线 — Slot 异常捕获 (v2.5)

`Slot::Run()` 用 `try-catch(...)` 包裹模块回调作为最后防线：

```cpp
try {
    func_(args...);           // 模块回调
    return true;
} catch (const std::exception& e) {
    std::cerr << "[Slot::Run] Exception: " << e.what() << std::endl;
    MarkDead();               // 不再被调用
    return false;
} catch (...) {
    std::cerr << "[Slot::Run] Unknown exception" << std::endl;
    MarkDead();
    return false;
}
```

一个第三方模块回调抛异常不会崩掉整个进程。异常后 slot 标记为 dead，从后续快照中排除。

## main.cpp — 只剩组装

```cpp
int main() {
    平台初始化
    注册模块 (PrintModule, LogModule, MetricsCollector)
    注册框架信号
    扫描插件
    ShellEngine engine(8, 4);
    engine.Run();
    engine.Shutdown();
}
```

main.cpp 从 262 行缩减到 74 行。循环逻辑、done_queue、输入线程、cv 同步都在 ShellEngine 里。

## 平台抽象层 (v2.5)

所有操作系统 API 集中在 `core/platform/`，提供统一接口：

```
core/platform/
├── platform.h              # 平台检测宏 + PLATFORM_EXPORT/IMPORT
├── file_system.h/.cpp      # FindFiles / FileExists / NormalizePath
├── shared_library.h/.cpp   # RAII 封装 (LoadLibrary / dlopen)
├── shared_memory.h/.cpp    # RAII 封装 (CreateFileMapping / shm_open+mmap)
├── process.h/.cpp          # Launch / CpuTimeUs / ExePath / ExeDir
└── console.cpp             # InitConsole / InitLeakDetection
```

- **此目录之外零 `#ifdef _WIN32`** — 整个框架使用 `PLATFORM_WINDOWS`/`PLATFORM_LINUX`/`PLATFORM_MACOS`
- **全面 RAII** — `SharedLibrary` 和 `SharedMemory` 在析构时自动清理
- **`PLATFORM_EXPORT`** 替代 `__declspec(dllexport)`，实现跨平台符号可见性
- **插件扫描** 使用 `FindFiles("plugins", "*.dll" 或 "*.so")` — 通过 `kSharedLibExt` 自动匹配平台扩展名

### 示例：改前 vs 改后

```cpp
// 改前（仅 Windows，手动清理）:
#ifdef _WIN32
HMODULE handle = LoadLibraryA(path);
auto create = (CreateFunc*)GetProcAddress(handle, "CreateModule");
// ... 使用模块 ...
FreeLibrary(handle);
#endif

// 改后（跨平台，RAII）:
auto lib = platform::SharedLibrary::Load(path);
auto create = lib->GetFunction<CreateFunc>("CreateModule");
// ... 使用模块 ...
// lib 析构自动调用 FreeLibrary 或 dlclose
```
