# 任务系统 — 分片、暂停、取消

一个 Task 是一串"分片"。每个分片 = 一次 EventBus 发射。分片之间可以暂停、恢复、取消。

## 数据流向（v2.5）

```
工人: while(task->Step(bus)) {}
  → bus.Emit("Calc.add", pack)     // 模块回调执行
  → ResultStore::PushResult(...)   // 结果落入仓库
  → tasks.Release(task)            // 槽位立即可复用
  → 主循环: DrainResults()         // 消费者按自己节奏批量取
```

不再有 `done_queue`。结果走 `ResultStore`——工人 Push，消费者 Drain。

## 普通命令（1 个分片）

```
-m:Calc -f:add -v:a|1,b|2
→ Task 有一个分片: {mod_id="Calc", func_id="add"}
→ Step() 发射 "Calc.add" → 模块回调 → 完成
```

## 多分片工作流

```cpp
REGISTER_FUNC("render", "逐帧渲染", {
    RenderFrame(frame_);
    frame_++;
    if (frame_ < total_) {
        auto next = std::make_unique<ParmarPack>();
        next->mod_id  = GetName();
        next->func_id = "render";
        pack->owner_task->PushShard(std::move(next));  // 追加下一帧
    }
    pack->success = true;
});
```

## 暂停 / 恢复

```
task->Pause();        // 当前分片跑完后暂停
task->Resume();       // 从断点继续
task->GetProgress();  // 0.0 ~ 1.0
```

暂停只在**分片之间**生效，当前正在跑的分片不受影响。

## 取消

```
task->Cancel();       // 状态 → FAILED，阻止后续分片
```

同样，当前分片跑完才生效。

## 死任务？分片内部无法打断

C++ 没法安全杀线程。如果一个分片进了死循环，`Cancel` 救不了。解决方案：把分片拆小（< 100ms）。

## ITaskPersistence — 任务状态持久化 (v2.7, 已集成暂停存储)

任务状态默认全在内存。进程退出 → PAUSED 任务丢失。
`ITaskPersistence` 是可插拔的持久化层，暂停任务写快照，`resume` 时读回重建。

### 暂停 → 保存 → 恢复 闭环

```
pause 命令 → task->Pause()                    // 打标记
  → Worker 跑完当前分片 → Step() 返回 false
  → Worker 检测 PAUSED → store->Save(task->ExportRecord())
  → Release(task)                             // 槽位归还

resume 命令 → store->Load(id) → pool.Acquire → task->Restore(rec)
  → Resume → Enqueue → 从断点继续
```

`Task::ExportRecord()` 把当前分片序列化成 `TaskRecord.shards_json`（JSON 数组），
`Task::Restore()` 反序列化回真实分片（mod_id / func_id / params 完整保留）。

### 接入方式

```cpp
// main.cpp — store 声明在 engine 之前（保证析构顺序）
auto taskStore = std::make_shared<MemPersistence>();
ShellEngine engine(cfg.pool_size, cfg.workers);
engine.SetTaskPersistence(taskStore.get());   // 框架层在暂停时保存快照
mgr.AddModule(std::make_unique<TaskManagerModule>(
    engine.GetPool(), engine.GetWorkers(), taskStore.get()));
```

`SetTaskPersistence(nullptr)`（默认）= 纯内存，暂停任务不落盘，行为与 v2.5 一致。

### 如何实现一个 ITaskPersistence 后端

开发者可自定义后端（FilePersistence / SqlitePersistence 等），只需实现 5 个虚方法：

| 方法 | 职责 |
|------|------|
| `Save(const TaskRecord&)` | 保存/更新快照。**幂等**，同一 task_id 可重复覆盖 |
| `Load(id) → optional<TaskRecord>` | 读取快照；不存在返回 nullopt |
| `Delete(id)` | 删除快照（任务完成后由 resume 流程调用） |
| `LoadAll() → vector<TaskRecord>` | 返回所有**非终态**记录（启动恢复用） |
| `GC()` | 清理终态（COMPLETED/FAILED）记录 |
| `IsAvailable()` | 后端是否可用；不可用则框架退化为纯内存 |

三条硬性约束：

1. **线程安全**：Worker 线程和主线程可能并发调用，内部必须加锁（参考 `MemPersistence` 的 mutex）。
2. **异常安全**：Save/Load/Delete 失败要静默处理，不抛异常（Worker 收尾抛异常会崩掉 shell）。
3. **生命周期**：后端必须比 ShellEngine 活得久（声明在 engine 之前）。

参考实现：
- `NullPersistence` — 默认，零开销空实现。
- `MemPersistence` — 进程内内存实现，重启丢失。
- `FilePersistence` / `SqlitePersistence` — 计划，按上述约束实现。
